# Project Module Configuration Ownership

Kickoff supplies reference identity, inert content and explicit project/deployment
choices. A reusable constant or binding mechanism belongs to its existing
implementing framework owner. This inventory covers root `config`, the structural
`modules/config` boundary and all seven module config contributions. Environment,
server and node runtime files are a separate deployment audit. Secrets, installed
records, historical receipts and setup-observation evidence are not relocation
inputs.

The retained categories below are not blanket exemptions for their contents.
Apply nSetup's mandatory default ownership gate to each declaration, including
standard provider wiring, technical defaults, schema policies and mixed
mechanism/selection objects. A previous inventory or an equal-value safety pin
does not close a newly identified ownership defect. Required owner migrations
must preserve actual project selections and destructive-operation boundaries.

  They bound destructive deployment scope, not reusable model inventories.
  Existing capabilities already own inert inventories. Do not move reset target
  selection into defaults or activate absent owners to eliminate historical names.

  Keep these customer topology facts separate from reset mechanics and grants.
- `copilot.runtimeRoleProfiles`: customer-project label, API/provider opt-ins,
  selected Ollama adapter, ingestion/retrieval/startup enablement, indexer identity,

  opt-ins. Their framework defaults remain independently disabled where applicable.
- `apiExposure.runtimeRoleProfiles`: deliberate deployment opt-ins and negative
  Online/Process exposure pins. Review these only when the runtime's API role is
  deliberately requalified; equality with an owner default is not permission to

- `backofficeApplicationInitialization`: project profiles, titles, content IDs,
  required modules/data and selected WCMS connection. Explicit USER triggers,
  approval policy and operator enterprise selectors remain part of the selected
  setup contract, not generic behavior to enable everywhere.
- `backofficeFunctionalModuleActivationData`: exact project-selected packages,
  target servers and database-coordinate bindings for those import targets.
  Generic activation/import implementation stays with BackOffice/nImport.

## Verification Boundary

`test/moduleConfigurationOwnership.test.js` checks the complete root/module hook
inventory, absence of copied mechanics, actual nConfig before/after role projection,
unrelated project contexts, Product acceptance consumer equivalence and final
Native/Docker owner activation. Framework owner tests cover defaults, missing
context and later overrides independently of Kickoff. The existing inheritance
and acceptance fixture tests assert inheritance instead of copied source values.

Configuration equivalence does not establish installed access, provider readiness,
data freshness or live acceptance. Parent integration must reconcile source pins,
headers and generated contracts, freeze the complete batch, then run the consolidated
tests. Do not refresh shared manifests or run broad suites while owners are still
editing. A rejected or missing runtime prerequisite remains a blocker, never an
excuse to copy authority back into this project or mutate a demo installation.

## Deployment Ownership Corrections

Commerce and WCMS inherit standard role-based provider, transport, observer and
source-schema definitions from the concrete framework owners. Native deployment
files retain endpoints, signed caller restrictions and reviewed qualification.
Docker retains explicit versioning-off role overrides until separately qualified.
The actual runtimeRole remains a deployment selection; domain role mappings do not.

Commerce Staged explicitly selects eWaste's Product intent-source contribution;
Commerce Online selects its DigitalCore integration contribution through package
runtimeConfigurationContributions. Generic owners keep neutral transport defaults.
These metadata selections do not activate eWaste, grant access or qualify sales.
Engagement discovers eWaste only for selected Telegram/in-app presentation files;
source trust, provider selection and credential references remain deployment policy.

Credential schema overlays select only logical credentialReference; nSystem derives
its wrapped path. CMS documentation baselines retain exact release/source pins and
derive only an unambiguous site from that exact qualified pack. Other roots remain
explicit. Reset profile residual services and required-service assertions were
compared to selected owner inventories: no duplicates were found. Their existing
destructive scope remains unchanged, with no automatic discovery expansion.

Owner and reference-adoption regression sources accompany these changes. Source
placement and formatting are not execution evidence; run the consolidated gates
only after the complete refactor/ownership review, then qualify live operations
separately. Never replay completed demo transactions for a configuration move.
